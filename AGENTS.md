# Правила спільної роботи над навчальними проєктами

## Мова і пояснення

- Спілкуйся з користувачем українською, якщо він не попросив іншу мову.
- Пояснюй просто, дружньо й по суті.
- Після суттєвої зміни вкажи, яку ідею з курсу вона закріплює.
- Не видавай готове рішення без пояснення ключової логіки.
- Не перевантажуй пояснення базовими деталями, які не стосуються завдання.
- Якщо доречно, завершуй одним коротким запитанням для самоперевірки.

## Загальний стиль коду

- Пиши читабельний, прямолінійний код без передчасних абстракцій.
- Сприймай перелічені технології як базовий стек, а не як закритий список дозволених інструментів.
- Перед написанням складної логіки перевіряй можливості платформи, наявні залежності та перевірені спеціалізовані бібліотеки.
- Пропонуй нову бібліотеку, якщо вона суттєво покращує безпеку, доступність, надійність або замінює великий обсяг складної ручної реалізації.
- Не додавай залежність заради кількох простих і зрозумілих рядків коду.
- Перед додаванням великої залежності або зміною архітектури коротко поясни користь, недоліки й альтернативи та отримай згоду користувача.
- Назви змінних, функцій, компонентів, файлів і папок — англійською та за змістом.
- Папки й звичайні файли називай малими літерами без пробілів; дотримуйся стилю наявного проєкту.
- Не змінюй архітектуру та інструменти без потреби.
- Спочатку перевикористовуй наявні утиліти й компоненти.
- Видаляй невикористані імпорти, змінні, закоментований код і діагностичні повідомлення.
- Форматуй код засобами, вже налаштованими у репозиторії.
- Не приховуй помилки порожніми `catch` або сумнівними значеннями за замовчуванням.

## HTML

- Використовуй семантичні теги відповідно до призначення контенту.
- Зберігай логічну ієрархію заголовків.
- На сторінці має бути один основний `main`.
- Використовуй `button` для дій та `a` для переходів.
- Додавай змістовний `alt` для контентних зображень і порожній `alt` для декоративних.
- Пов'язуй поля форми з `label`; не використовуй placeholder як заміну підпису.
- Зберігай правильну вкладеність і форматування з відступом у два пробіли.

## CSS

- Переважно використовуй селектори класів із низькою специфічністю.
- Не використовуй `!important` без обґрунтованої виняткової причини.
- Будуй адаптивність за підходом Mobile First.
- Використовуй `gap` для відстаней між елементами flex/grid-контейнера.
- Не застосовуй абсолютне позиціонування для основної розкладки.
- Додавай стани `hover`, `focus` і видимий `focus-visible` для інтерактивних елементів.
- Анімуй переважно `transform` та `opacity`; враховуй `prefers-reduced-motion`.

## Tailwind CSS і стилізація

- Для нових сольних React і Next.js проєктів за замовчуванням пропонуй Tailwind CSS.
- Перед початком перевіряй стек проєкту: якщо Tailwind уже налаштований, використовуй його; якщо ні — встановлюй лише в новому проєкті або після прямої згоди користувача.
- Використовуй стандартні utility-класи Tailwind замість написання еквівалентного CSS вручну.
- Будуй адаптивність за Mobile First через стандартні breakpoint-префікси Tailwind.
- Для станів використовуй варіанти `hover:`, `focus:`, `focus-visible:`, `disabled:` та інші доречні варіанти.
- Дотримуйся стандартної шкали відступів, розмірів, кольорів і радіусів; довільні значення на кшталт `w-[317px]` використовуй лише коли цього справді вимагає дизайн.
- Повторюваний набір класів винось у компонент, а не копіюй між багатьма місцями.
- Для умовних класів використовуй наявні `clsx`, `classnames` або функцію `cn`; не створюй нову утиліту, якщо в проєкті вже є відповідна.
- Не створюй CSS Module, якщо стилі зрозуміло виражаються стандартними класами Tailwind.
- CSS Modules або окремий CSS використовуй для складних анімацій, нестандартних селекторів, сторонніх віджетів чи випадків, де довгий `className` суттєво погіршує читабельність.
- Глобальний CSS залишай для reset, шрифтів, CSS-змінних, базових стилів документа та справді глобальних правил.
- Не змішуй Tailwind і CSS Modules для одного простого компонента без конкретної причини.
- Не встановлюй компонентну бібліотеку лише заради базових елементів; для складних доступних компонентів спочатку оціни перевірену бібліотеку.

## JavaScript і TypeScript

- Використовуй `const` за замовчуванням, `let` — лише для переприсвоєння; не використовуй `var`.
- У навчальних JavaScript-репозиторіях використовуй одинарні лапки та крапки з комою, якщо конфігурація проєкту не задає інше.
- Одна функція повинна мати одну зрозумілу відповідальність.
- Називай функції дієсловами, булеві значення — з префіксами `is`, `has`, `can` або `should`.
- Віддавай перевагу раннім поверненням замість глибокої вкладеності.
- Не мутуй дані без потреби.
- Порівнюй значення через `===` і `!==`; не покладайся на неявне приведення типів.
- Вибирай метод масиву за результатом: `map` для перетворення, `filter` для відбору, `find` для одного елемента, `reduce` для підсумку.
- Відокремлюй отримання даних, обчислення та відображення в DOM.
- Не вставляй неперевірені дані через `innerHTML`.
- Обробляй асинхронні помилки й показуй користувачу зрозумілий стан завантаження або помилки.
- Після завершення прибирай навчальні `console.log` та перевіряй консоль браузера.
- У TypeScript не використовуй `any`, якщо тип можна коректно описати.

## React і Next.js

- Компонент повинен виконувати одну основну роль.
- Типізуй props окремим зрозумілим типом; не використовуй `any`.
- Стан зберігай якомога ближче до місця використання.
- Не дублюй похідні дані у стані — обчислюй їх під час рендеру.
- Не мутуй props або state; для залежного оновлення використовуй функціональну форму setter.
- Використовуй стабільні ключі списків, а не індекс, якщо порядок може змінюватися.
- Побічні ефекти залишай у `useEffect`; не використовуй ефект для звичайних обчислень.
- Вказуй усі залежності ефекту та очищай слухачі, таймери й підписки.
- Перед створенням нового компонента перевір наявні компоненти проєкту.
- Серверні дані зберігай у React Query або отримуй на сервері, а не дублюй у локальному стані.
- Query key має містити всі параметри, що впливають на результат; після mutation онови відповідний кеш.
- У Next.js поважай межі серверних і клієнтських компонентів; `use client` додавай лише за потреби.
- Тримай клієнтську межу якомога нижче в дереві компонентів.
- Перевіряй авторизацію на сервері; приховування елемента інтерфейсу не є захистом.
- Не передавай секрети або приватні токени до клієнтського коду.

## Node.js і REST API

- Розділяй router, controller, service/model, middleware та validation; не змішуй їхню відповідальність.
- Дотримуйся REST: ресурси називай іменниками у множині та використовуй правильні HTTP-методи й статуси.
- Валідуй `body`, `params`, `query` і файли на вході; не передавай довільні клієнтські об'єкти прямо в MongoDB.
- Контролери мають бути короткими: отримати дані запиту, викликати сервіс і сформувати відповідь.
- Передавай асинхронні помилки в централізований error middleware і не розкривай клієнту внутрішні деталі.
- Підключайся до бази до запуску сервера; рядки підключення й секрети тримай лише у змінних оточення.
- Ніколи не повертай password hash, session token, cookie або інші секрети в API чи логах.
- Хешуй паролі через перевірену бібліотеку; не зберігай і не надсилай пароль у відкритому вигляді.
- Для кожної операції з приватним ресурсом перевіряй не тільки його ID, а й власника.
- Обмежуй пагінацію, поля сортування, фільтри, розмір JSON-body та завантажуваних файлів.
- Для upload використовуй whitelist типів, унікальні імена й гарантоване очищення тимчасових файлів.
- Усі API-відповіді повинні мати послідовну структуру в усьому проєкті.

## Перевірка результату

- Запускай наявні перевірки форматування, lint, типів, тестів і збірки відповідно до масштабу зміни.
- Для інтерфейсів перевіряй мобільний, планшетний і десктопний вигляд.
- Перевіряй стани завантаження, порожніх даних, помилок і клавіатурної навігації.
- Не оголошуй роботу завершеною, якщо релевантна перевірка не виконана або завершилася помилкою.
